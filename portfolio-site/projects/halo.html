Halo

Par Lhoussaine Thoumi · Mis à jour le 1 août 2026

Refonte d'une application de rencontre en Clean Architecture / DDD : microservices .NET 9, temps réel SignalR, contrat API explicite.

01

Contexte & problème métier

Au départ, l'application de rencontre fonctionnait, mais elle avait été construite comme un exercice pédagogique : la logique métier traînait dans les controllers, aucune notion de « match » n'existait vraiment en base, et la sécurité tournait encore sur sa configuration par défaut. Le vrai problème n'était donc pas fonctionnel (tout marchait) mais structurel : sans donner une forme explicite au domaine métier, impossible de faire évoluer le produit, qu'il s'agisse de notifier un match, d'en garder l'historique ou de fiabiliser la modération.

Le projet Halo reconstruit cette base couche par couche, en traitant chaque décision d'architecture comme le ferait une vraie équipe produit : partir d'un besoin métier, documenter le compromis, livrer, puis mesurer.

02

Objectifs fonctionnels & techniques

Fonctionnels

  • Profils, photos modérées, sélection quotidienne de profils
  • Likes réciproques → match explicite et daté
  • Messagerie et présence en temps réel
  • Back-office de modération photo

Techniques

  • Clean Architecture + DDD sur le service principal
  • Conformité SOLID vérifiée par audit, pas supposée
  • Migrations EF Core traçables, avec backfill de données historiques
  • Contrat API explicite (OpenAPI) → client TypeScript généré

04

Composants, en détail

Frontend
Angular 20 en standalone components, avec les signals pour l'état réactif. NgRx n'est pas encore justifié vu la surface d'état actuelle de l'app. Le service MemberService type ses requêtes directement depuis le schéma OpenAPI généré : la moindre dérive de contrat casse la compilation TypeScript avant même d'atteindre la prod.
Api
Des controllers ASP.NET Core volontairement minces : authentification JWT, validation FluentValidation, puis délégation immédiate à l'Application. La documentation est générée via Swashbuckle, et ce même Swagger sert de source pour générer le client TypeScript.
Application
MatchingService orchestre la logique métier, épaulé par des interfaces de rôle propres à chaque cas d'usage (IMatchingUnitOfWork, ILikesUnitOfWork…) : chaque consommateur ne voit que les repositories qu'il appelle réellement, conformément à l'ISP.
Domain
Les value objects Email et AgeRange, et l'agrégat Match dont l'invariant d'ordre déterministe entre les deux membres est imposé directement dans le constructeur, pas dans le repository, où il pourrait être contourné.
Infrastructure
Les repositories EF Core et le UnitOfWork (une instance scoped par requête, donc une seule transaction), plus des migrations versionnées. L'une d'elles embarque même un backfill SQL manuel pour reconstituer l'historique des matchs déjà existants.
Base de données
SQL Server, avec un index unique sur la paire ordonnée de membres : un doublon de match est rejeté au niveau de la base, pas seulement filtré côté code.
Messaging
RabbitMQ gère les événements inter-services, par exemple l'approbation d'une photo. Le pattern Outbox transactionnel n'est pas encore en place. L'état de ce chantier est détaillé plus loin, en section 8.
Temps réel
SignalR fait tourner la messagerie et la présence en ligne, via MessageHub et PresenceHub.
Observabilité
Serilog et Seq centralisent les logs structurés. Les métriques (Prometheus/Grafana) et le tracing distribué restent à construire.

05

Choix techniques & alternatives écartées

.NET 9 / ASP.NET Core

L'écosystème est mature, la performance au rendez-vous, et la prochaine LTS approche. Node/NestJS aurait sa place ailleurs, mais colle moins bien à un domaine aussi fortement typé que celui-ci.

SQL Server + EF Core

Les transactions ACID et des contraintes d'unicité fiables comptaient plus qu'un schéma flexible. Les relations entre membre, match et message sont de toute façon intrinsèquement relationnelles, ce qui a écarté MongoDB assez vite.

RabbitMQ

Le découplage événementiel qu'il offre suffit largement au volume actuel, et il s'opère simplement depuis Docker Compose. Kafka aurait du sens pour du streaming à fort débit ou du replay d'événements, pas encore pour ce volume ; il rejoindra la stack en complément plus tard, pas en remplacement.

SignalR

Le temps réel est géré nativement par ASP.NET Core, sans infrastructure séparée à opérer. Repartir d'un WebSocket brut aurait simplement obligé à réinventer la reconnexion, les groupes et le fallback que SignalR fournit déjà.

Angular 20 + Signals

La réactivité fine qu'apportent les signals suffit à cette taille d'application, sans le coût cognitif d'un store global. NgRx trouvera sa place le jour où l'état partagé entre fonctionnalités se complexifiera. Prématuré aujourd'hui.

OpenAPI + client TS généré

Le contrat devient une source de vérité unique : la moindre dérive entre backend et frontend se transforme en erreur de compilation plutôt qu'en bug découvert en production. C'est exactement ce qu'évite cette approche face à des DTO dupliqués à la main côté client.

06

Patterns d'architecture

Clean Architecture

Domain, Application, Infrastructure, Api, avec une règle de dépendance à sens unique. Le Domain, par exemple, n'a aucune référence à EF Core.

Domain-Driven Design

Les value objects Email et AgeRange, et l'agrégat Match, portent chacun leurs propres invariants plutôt que de les laisser traîner dans les controllers.

SOLID · Interface Segregation

Un IUnitOfWork unique exposait autrefois tous les repositories à tous les consommateurs. Il a depuis été décomposé en interfaces de rôle (IMatchingUnitOfWork, ILikesUnitOfWork…), assemblées sur une seule et même implémentation concrète.

Repository + Unit of Work

Ce pattern découple le Domain d'EF Core, avec une limite bien identifiée : une façade de ce genre glisse vite vers le God Object si elle n'est pas segmentée, d'où le refactor ISP évoqué juste au-dessus.

API-First

Le contrat OpenAPI est généré depuis le code puis consommé pour typer le client, jamais l'inverse.

Event-Driven (partiel)

Des consommateurs RabbitMQ sont déjà en place pour certains flux, mais le pattern Outbox transactionnel n'y est pas encore : un événement peut aujourd'hui partir sans garantie atomique avec l'écriture SQL. Le problème est identifié et priorisé pour la suite.

07

Flux complet d'une requête

Exemple réel : un like qui devient un match, du clic dans le navigateur à la ligne SQL.

01Angular envoie POST /api/likes/{targetId} avec le bearer JWT.
02LikesController vérifie qu'on ne se like pas soi-même, lit le like existant via ILikesUnitOfWork.
03Le like est ajouté au DbContext (pas encore flush), puis MatchingService.HandleLikeAddedAsync est appelé.
04Le service vérifie la réciprocité via IMatchingUnitOfWork, puis l'idempotence (pas de match déjà existant).
05Match.Create() applique l'invariant du Domain (ordre déterministe des ids) et génère l'entité.
06Un seul SaveChangesAsync persiste like + match dans la même transaction implicite EF Core.
07SQL Server applique l'index unique sur la paire : un doublon échouerait même si le code applicatif avait un trou.

08

Sécurité, performance, scalabilité, DevOps, observabilité

Sécurité

Authentification JWT en place et fonctionnelle. Le durcissement production (validation stricte de l'émetteur/audience, secrets en coffre plutôt qu'en configuration, rate limiting) est un chantier identifié et planifié, pas encore livré.

Performance

Pagination sur les listes de membres, index ciblés (dont l'unicité de Match), migrations incrémentales plutôt que des rebuilds de schéma.

Scalabilité

Découpage en 3 services indépendants (core-api, chatbot, media) déployables séparément. Limite connue : SignalR est mono-instance aujourd'hui, sans backplane Redis, ce qui bloque un scaling horizontal, déjà en roadmap.

DevOps

Stack complète orchestrée en Docker Compose (8 services). CI GitHub Actions couvre aujourd'hui le build/déploiement du Core API ; les 3 autres services ne sont pas encore automatisés.

Observabilité

Logs structurés centralisés via Serilog + Seq, déjà exploités pour diagnostiquer des bugs réels pendant le développement (voir section suivante). Métriques et tracing distribué (Prometheus/Grafana/OpenTelemetry) ne sont pas encore en place.

09

Difficultés rencontrées & compromis

Rien de ce qui suit n'était prévu au départ : ce sont des problèmes réels, rencontrés puis résolus pendant la construction.

Un bug de DI a révélé la violation ISP avant même l'audit

La génération d'une migration EF Core a échoué (Unable to resolve service for type IMatchRepository) parce que le service métier dépendait d'un repository jamais enregistré seul dans le container : seul IUnitOfWork l'était. Ce même symptôme a ensuite justifié le refactor en interfaces de rôle.

Un bug de seed invisible en local, découvert seulement dans les logs Docker

Après la restructuration en couches, le chemin de lecture du fichier de seed pointait encore vers l'ancien dossier. L'erreur était avalée par un try/catch existant : les health checks passaient, la base restait vide. Retrouvé en lisant les logs Seq du conteneur, pas en local.

Un diamant d'interfaces pendant le refactor ISP

Complete() déclaré séparément dans deux interfaces de rôle compilait via la classe concrète mais devenait ambigu via le type composé. Corrigé en isolant l'opération commune dans une interface de base partagée.

Compromis assumé : le scope de cette première phase se limite volontairement au socle (Clean Architecture, DDD, SOLID, contrat API) avant d'empiler CQRS, Kafka ou Outbox. Une fondation qui ne compile pas proprement rend tout le reste plus coûteux à corriger plus tard.
