C#

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Le langage que j'utilise au quotidien sur mes projets .NET (dont Hallo) : ce qui distingue un value type d'un reference type, comment async/await évite de bloquer un thread, et les pièges qui reviennent le plus souvent en revue de code.

Vue d'ensemble

C# est un langage fortement typé, orienté objet avec des emprunts fonctionnels de plus en plus marqués (LINQ, pattern matching, records). La grande majorité des bugs subtils que je croise viennent de deux zones précises : la confusion entre types valeur et référence, et un usage incorrect d'async/await, les deux premières sections de cette fiche.

Concepts clés

Value types vs reference types
Un struct (int, DateTime, un struct custom) est copié par valeur à chaque affectation ou passage en paramètre ; une class est copiée par référence : deux variables pointent alors vers le même objet en mémoire. Confondre les deux produit des bugs de mutation inattendue.
Nullable reference types
Depuis C# 8, #nullable enable fait du compilateur un allié : string? annonce explicitement qu'une référence peut être nulle, string seul ne le devrait jamais être. Le compilateur avertit dès qu'un chemin de code contredit cette promesse.
Records
Type de référence (ou record struct) avec égalité par valeur et immutabilité générées automatiquement : l'outil naturel pour un DTO ou un value object qui ne doit pas changer après sa création.
Pattern matching
Le switch expression et les patterns is permettent de décomposer un type ou une valeur directement dans la condition, sans cascade de if/else ni cast manuel.
Génériques
Du code type-safe et réutilisable sans dupliquer par type ni perdre en performance : List<T> évite le boxing qu'imposerait une collection non générique sur des types valeur.

Async/await en détail

async/await ne crée pas de nouveau thread : il libère le thread appelant pendant l'attente d'une opération I/O (requête HTTP, disque, base de données), qui peut alors servir une autre requête. C'est ce qui permet à une API ASP.NET Core de tenir des milliers de requêtes concurrentes avec un pool de threads restreint.

Task vs Task<T> vs ValueTask<T>
Task/Task<T> représentent une opération asynchrone en cours. ValueTask<T> évite une allocation sur le tas quand le résultat est très souvent déjà disponible de façon synchrone (un cache qui répond en mémoire la plupart du temps), une micro-optimisation à réserver aux chemins chauds mesurés.
Async all the way
Un appel bloquant (.Result, .Wait()) sur une Task depuis un contexte synchrone qui possède un SynchronizationContext (ancien ASP.NET, WPF) peut provoquer un deadlock : le thread attend la fin de la tâche, mais la tâche attend de pouvoir reprendre la main sur ce même thread. ASP.NET Core n'a plus ce contexte par défaut, mais la règle reste : ne jamais bloquer sur de l'async.
CancellationToken
Propage une demande d'annulation à travers toute une chaîne d'appels asynchrones, indispensable pour arrêter une requête EF Core quand le client HTTP a fermé la connexion, plutôt que de laisser la requête tourner pour rien.

LINQ & collections

LINQ unifie la syntaxe de requête sur des collections en mémoire (LINQ to Objects) et sur une base de données (LINQ to Entities via EF Core), mais leur exécution diffère fondamentalement.

Exécution différée (deferred execution)
Un IEnumerable<T> issu de Where/Select ne s'exécute qu'au moment où il est énuméré (foreach, .ToList()), pas à sa déclaration. Énumérer deux fois la même requête ré-exécute deux fois le filtre, ou pire, deux fois la requête SQL avec EF Core.
IEnumerable vs IQueryable
IEnumerable<T> exécute le filtre en mémoire, côté application. IQueryable<T> (EF Core) traduit l'expression LINQ en SQL et ne rapatrie que les lignes filtrées. Utiliser IEnumerable par erreur sur une grande table charge tout en mémoire avant de filtrer.
Matérialiser au bon moment
.ToList() force l'exécution immédiate et fige le résultat, à faire une fois que la requête est complète, jamais avant, pour ne pas perdre le bénéfice de la traduction SQL sur les opérations suivantes.

Cheat sheet

// Pattern matching
var aire = forme switch
{
    Cercle c => Math.PI * c.Rayon * c.Rayon,
    Carre s => s.Cote * s.Cote,
    _ => throw new ArgumentException("Forme inconnue")
};

// Records : égalité par valeur, immutabilité
public record Point(double X, double Y);
var p1 = new Point(1, 2);
var p2 = p1 with { X = 5 };   // copie immuable, seul X change
Console.WriteLine(p1 == new Point(1, 2)); // True : égalité par valeur

// Async/await avec annulation
public async Task<Member?> GetMemberAsync(int id, CancellationToken ct)
{
    return await _db.Members
        .FirstOrDefaultAsync(m => m.Id == id, ct);
}

// LINQ : IQueryable traduit en SQL par EF Core
var emailsActifs = _db.Members
    .Where(m => m.IsActive)
    .OrderBy(m => m.LastName)
    .Select(m => m.Email)
    .ToListAsync();   // une seule requête SQL, exécutée ici

Bonnes pratiques

Async de bout en bout

Une méthode async appelée en .Result quelque part dans la chaîne annule tout le bénéfice du non-bloquant : la propager en async jusqu'au point d'entrée.

Nullable reference types activés

<Nullable>enable</Nullable> dans le csproj, dès le début d'un projet : ajouté après coup sur une grosse base de code, les warnings deviennent vite ingérables.

Records pour les DTO

Un DTO ou un value object qui ne doit pas changer après sa création devient un record : égalité par valeur et immutabilité gratuites, sans code de plomberie.

using declarations

Un IDisposable (connexion, flux) libéré via using var conn = ...; plutôt qu'un Dispose() manuel qu'un chemin d'exception peut faire sauter.

Dependency Injection native

Le conteneur intégré d'ASP.NET Core suffit dans l'immense majorité des cas ; un conteneur tiers ne se justifie que pour des besoins avancés précis (interception, cycles de vie personnalisés).

ConfigureAwait dans les bibliothèques

ConfigureAwait(false) évite de revenir sur le contexte de synchronisation d'origine, pertinent dans une librairie partagée consommée par des contextes variés (UI, ASP.NET classique), mais inutile dans une app ASP.NET Core qui n'a plus ce contexte.

Questions d'entretien fréquentes

Value type vs reference type, concrètement ?

Un value type est copié à chaque affectation ou passage en paramètre : modifier la copie ne touche pas l'original. Un reference type partage la même instance entre toutes les variables qui la référencent, donc modifier l'une modifie ce que voient toutes les autres.

Comment fonctionne async/await sous le capot ?

Le compilateur transforme la méthode en machine à états : à chaque await, le thread est libéré pendant l'attente de l'opération I/O, et l'exécution reprend sur un thread du pool (pas forcément le même) une fois le résultat disponible.

IEnumerable vs IQueryable ?

IEnumerable exécute la requête en mémoire, côté application. IQueryable construit un arbre d'expression traduit en SQL par le provider (EF Core) et exécuté côté base de données. La différence devient critique sur de gros volumes.

Pourquoi utiliser un record plutôt qu'une classe classique ?

Pour un type dont l'identité repose sur ses valeurs plutôt que sur une référence (un DTO, un value object) : égalité par valeur, immutabilité et une syntaxe with pour créer une copie modifiée, sans écrire ce code à la main.

Que fait le garbage collector, en résumé ?

Il libère automatiquement la mémoire des objets du tas managé qui ne sont plus référencés, en travaillant par générations (0, 1, 2) : les objets récents sont collectés plus fréquemment, sur l'hypothèse qu'un objet qui survit longtemps a plus de chances de continuer à survivre.
