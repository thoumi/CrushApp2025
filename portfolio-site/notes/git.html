Git

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Git devient simple dès qu'on arrête de le voir comme une liste de commandes à mémoriser et qu'on le voit pour ce qu'il est : un graphe orienté de commits. Le reste (branches, rebase, reflog) n'est que de la manipulation de ce graphe.

Vue d'ensemble

Un commit est un instantané complet du projet, pas un simple diff, avec un pointeur vers son ou ses parents. Une branche n'est qu'une étiquette mobile qui pointe vers un commit : la créer ou la supprimer ne coûte rien et ne déplace aucun fichier.

Le modèle mental

Les trois zones
Working directory (fichiers sur le disque) → staging area / index (git add, ce qui sera dans le prochain commit) → historique local (git commit). Comprendre ces trois zones dissout la moitié des confusions sur Git.
HEAD
Un pointeur vers le commit actuellement extrait (checked out), généralement via une branche. Un HEAD détaché pointe directement vers un commit, sans branche.
Remote
Une référence vers un autre dépôt (origin). fetch rapatrie son historique sans y toucher localement ; pull fait fetch puis fusionne (ou rebase).
Reflog
Le journal local de tous les déplacements de HEAD, y compris après un reset ou un rebase raté. C'est le vrai filet de sécurité : tant qu'un commit apparaît dans le reflog, il est récupérable.

Cheat sheet

# Explorer
git log --oneline --graph --all
git status
git diff --staged

# Corriger
git commit --amend                 # modifier le dernier commit (pas encore publié)
git reset --soft HEAD~1            # annule le commit, garde les changements en staging
git checkout -- fichier.txt        # jette les modifs locales non commitées
git restore --staged fichier.txt   # retire du staging sans perdre les modifs

# Sauver du travail en cours
git stash
git stash pop

# Investiguer un bug introduit
git bisect start
git bisect bad
git bisect good v1.2

Rebase vs merge

Merge

Crée un commit de fusion qui préserve l'historique exact, y compris les branches parallèles. Sûr sur une branche déjà partagée/publiée.

Rebase

Rejoue les commits d'une branche sur une nouvelle base : historique linéaire, plus lisible. À réserver aux commits pas encore poussés : rebaser une branche déjà partagée réécrit son historique et casse le travail de toute autre personne dessus.

Rebase interactif

L'outil pour nettoyer une série de commits locaux avant de les partager : regrouper, réordonner, reformuler. Jamais sur des commits déjà poussés et partagés.

git rebase -i HEAD~4

pick a1b2c3d Ajoute le formulaire de profil
squash e4f5g6h Corrige une faute de frappe
reword h7i8j9k Ajoute la validation email
drop   k1l2m3n Commit de debug à supprimer

squash fusionne un commit dans le précédent (utile pour un « fix typo » qui n'a pas sa place seul dans l'historique), reword réécrit uniquement le message, drop supprime le commit. Le résultat : un historique qui raconte une intention claire plutôt que le désordre réel du développement.

Workflows d'équipe

GitHub flow

Une branche par fonctionnalité depuis main, pull request, revue, merge. Simple et adapté au déploiement continu, c'est celui que j'utilise sur mes projets solo comme en équipe restreinte.

Git flow

Des branches dédiées (develop, release/*, hotfix/*) pour des cycles de release plus formels. Plus lourd, pertinent quand plusieurs versions doivent être maintenues en parallèle.

Trunk-based development

Des branches très courte durée (moins d'un jour), fusionnées fréquemment sur main derrière des feature flags plutôt que des branches longues : le modèle qui s'accorde le mieux avec un déploiement continu réel.

Questions d'entretien fréquentes

Différence entre git fetch et git pull ?

fetch rapatrie les références distantes sans toucher à la branche locale ; pull fait un fetch puis fusionne (ou rebase) automatiquement dans la branche courante.

Comment annuler un commit déjà poussé sans réécrire l'historique ?

git revert, qui crée un nouveau commit inverse, plutôt que reset --hard qui réécrirait un historique déjà partagé.

Qu'est-ce qu'un HEAD détaché ?

HEAD pointe directement sur un commit plutôt que sur une branche. Tout nouveau commit dans cet état devient orphelin si on change de branche sans en créer une nouvelle à cet endroit.

Pourquoi ne jamais rebaser une branche déjà partagée ?

Le rebase réécrit les commits (nouveaux SHA), donc l'historique de toute personne qui a déjà tiré cette branche diverge du sien. Résultat : conflits en cascade et confusion sur quel commit est le « bon ». Sur du travail publié, merge ou revert restent les options sûres.

Quand préférer trunk-based development à Git flow ?

Dès que l'objectif est un déploiement continu réel : des branches longue durée (comme develop) accumulent des divergences coûteuses à réconcilier. Git flow reste pertinent quand plusieurs versions doivent être maintenues et patchées en parallèle.
