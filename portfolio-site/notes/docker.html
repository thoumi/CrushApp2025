Docker

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Un pense-bête technique que je tiens à jour au fil de ma pratique DevOps : ce que Docker résout, comment un Dockerfile devient une image puis un conteneur, et les commandes que je réutilise vraiment en local et en CI.

Vue d'ensemble

Docker empaquette une application et toutes ses dépendances dans une image immuable, exécutée ensuite comme conteneur isolé. L'intérêt n'est pas la virtualisation en soi (les conteneurs partagent le noyau de l'hôte, contrairement à une VM) mais la garantie que l'environnement d'exécution est identique du poste du développeur jusqu'à la production : « build once, run anywhere ».

docker buildimage en couches

docker runconteneur (processus isolé)

Concepts clés

Image vs conteneur
L'image est un artefact immuable en couches (layers), en lecture seule. Le conteneur est une instance en cours d'exécution de cette image, avec une fine couche inscriptible par-dessus. Une même image peut donner naissance à N conteneurs indépendants.
Layers & cache de build
Chaque instruction du Dockerfile crée une couche mise en cache. Ordonner le Dockerfile du moins volatil (dépendances) au plus volatil (code source) maximise la réutilisation du cache et accélère les builds CI.
Volumes
Stockage persistant géré par Docker, indépendant du cycle de vie du conteneur. Indispensable pour les données qui doivent survivre à un docker rm (bases de données, uploads).
Réseau
Par défaut, les conteneurs d'un même réseau bridge défini par l'utilisateur se résolvent par leur nom de service. C'est ce qui permet à un backend de joindre db:5432 sans IP en dur.
Registry
Docker Hub, GitHub Container Registry ou un registry privé (ACR, ECR) stockent et versionnent les images taguées, point de passage obligé entre le CI et le déploiement.

Réseau en détail

Docker propose plusieurs pilotes réseau, chacun pour un cas d'usage précis, et choisir le bon évite bien des « ça ne se joint pas » en debug.

bridge (défaut)

Réseau privé isolé sur l'hôte. Le réseau bridge par défaut ne fait pas de résolution DNS par nom ; un réseau bridge défini par l'utilisateur (docker network create), lui, résout chaque conteneur par son nom de service.

host

Le conteneur partage directement la pile réseau de l'hôte, sans isolation ni NAT : un gain de performance au prix de l'isolation, à réserver à des cas ciblés (agents de monitoring, par exemple).

none

Aucune interface réseau. Utile pour un traitement batch qui ne doit avoir aucun accès réseau, par principe de moindre privilège.

overlay

Réseau qui s'étend sur plusieurs hôtes Docker (Swarm), la brique qui permet à des conteneurs sur des machines différentes de se joindre comme s'ils étaient sur le même réseau local.

Exposer un port (-p 8080:80) publie un mapping hôte→conteneur. Sans -p, un conteneur reste joignable par les autres conteneurs du même réseau via son port interne, mais invisible depuis l'extérieur de l'hôte. Cette distinction revient souvent en entretien.

Cheat sheet

Les commandes que j'utilise le plus souvent, classées par intention plutôt que par ordre alphabétique.

# Cycle de vie image / conteneur
docker build -t app:1.0 .
docker run -d --name app -p 8080:80 app:1.0
docker ps -a                     # tous les conteneurs, y compris arrêtés
docker stop app && docker rm app

# Inspection & debug
docker logs -f app
docker exec -it app sh           # ouvrir un shell dans le conteneur
docker inspect app               # config réseau, volumes, env...
docker stats                     # CPU / mémoire en direct

# Nettoyage
docker system df                 # espace disque utilisé
docker system prune -a           # supprime images/conteneurs orphelins

# Réseau & volumes
docker network ls
docker volume ls
docker network create app-net
docker run -d --network app-net --name db postgres:16

# Build avancé
docker build --build-arg VERSION=1.2 -t app:1.2 .
docker buildx build --platform linux/amd64,linux/arm64 -t app:1.0 --push .

Docker Compose

Dès qu'une stack dépasse un seul conteneur (API + base + cache), Compose déclare l'ensemble des services dans un seul fichier YAML versionné avec le code.

services:
  api:
    build: .
    ports: ["8080:80"]
    environment:
      ConnectionStrings__Default: "Host=db;Database=app"
    depends_on: [db]
  db:
    image: postgres:16
    volumes: ["db_data:/var/lib/postgresql/data"]
volumes:
  db_data:

docker compose up -d démarre toute la stack, docker compose logs -f api suit un service en particulier. C'est la même logique que j'utilise pour orchestrer les 8 services de Hallo (voir l'étude de cas complète).

Sécurité de l'image

Une image mal construite reste le vecteur d'attaque le plus sous-estimé d'une stack conteneurisée : la sécurité se joue dès le Dockerfile, pas seulement au runtime.

Scan de vulnérabilités
Docker Scout, Trivy ou Grype analysent chaque layer à la recherche de CVE connues dans les paquets installés, à intégrer directement dans le pipeline CI avant la publication sur le registry.
Images de base minimales
Une image alpine ou distroless réduit drastiquement la surface d'attaque par rapport à une base ubuntu complète : moins de paquets installés, moins de CVE possibles, et souvent aucun shell exploitable en cas de compromission.
Lecture seule & capacités réduites
--read-only interdit toute écriture dans le système de fichiers du conteneur en dehors des volumes déclarés ; --cap-drop=ALL retire les privilèges Linux non utilisés (un conteneur web n'a par exemple aucune raison de pouvoir changer l'heure système).
Signature & provenance
Docker Content Trust ou Sigstore/cosign signent une image au moment du build, pour garantir en production qu'elle provient bien du pipeline CI attendu et n'a pas été altérée entre-temps.

Bonnes pratiques

Images multi-stage

Compiler dans une étape build, ne copier que l'artefact final dans l'image d'exécution : des images 5 à 10x plus légères, sans SDK ni outils de build en production.

Ne jamais tourner en root

USER app dans le Dockerfile réduit la surface d'attaque si le conteneur est compromis.

Tags explicites

:latest rend les déploiements non reproductibles. Un tag de version ou le SHA du commit garantit qu'on sait exactement ce qui tourne.

.dockerignore

Exclure node_modules, .git, les secrets locaux : build plus rapide, image plus légère, rien de sensible copié par erreur.

Healthchecks

Un HEALTHCHECK ou une sonde d'orchestrateur détecte un conteneur « up » mais bloqué, avant que ça n'impacte les utilisateurs.

Secrets hors de l'image

Jamais de mot de passe en ENV dans le Dockerfile : ça reste lisible dans l'historique des layers. Variables d'environnement injectées au run, ou secret manager.

Questions d'entretien fréquentes

Différence entre une image et un conteneur ?

L'image est un artefact statique en couches ; le conteneur est un processus qui exécute cette image, avec son propre système de fichiers en écriture et son propre espace réseau/PID.

Pourquoi un build multi-stage ?

Pour séparer les outils nécessaires à la compilation de l'image finale d'exécution, et réduire drastiquement la taille et la surface d'attaque de l'image livrée.

Comment un conteneur persiste-t-il des données ?

Via un volume nommé géré par Docker ou un bind mount vers l'hôte ; jamais dans la couche inscriptible du conteneur, supprimée avec lui.

CMD vs ENTRYPOINT ?

ENTRYPOINT fixe le binaire exécuté et n'est pas facilement écrasé ; CMD fournit les arguments par défaut, remplaçables au docker run.

Pourquoi éviter le réseau bridge par défaut au profit d'un réseau créé explicitement ?

Le bridge par défaut ne fait pas de résolution DNS par nom de conteneur, seulement par IP, ce qui devient fragile dès qu'un conteneur redémarre et change d'IP. Un réseau bridge défini par l'utilisateur résout chaque service par son nom, exactement comme le fait Compose en coulisses.

Comment réduire la surface d'attaque d'une image en production ?

Base minimale (alpine/distroless), utilisateur non-root, scan de vulnérabilités en CI (Trivy), et --cap-drop=ALL au runtime pour ne garder que les privilèges Linux réellement nécessaires.
