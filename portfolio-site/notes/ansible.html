Ansible

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Automatiser la configuration d'un parc de serveurs sans agent à installer partout : Ansible se connecte en SSH, décrit l'état désiré en YAML, et ne modifie que ce qui diverge de cet état.

Vue d'ensemble

Contrairement à Puppet ou Chef, Ansible ne nécessite aucun agent résident sur les machines gérées : il pousse ses instructions par SSH (ou WinRM côté Windows) et s'exécute, puis repart. Son unité de travail est le playbook, un fichier YAML qui décrit une séquence de tâches idempotentes : les rejouer ne change rien si l'état désiré est déjà atteint.

Concepts clés

Inventory
La liste des machines cibles, organisées en groupes ([web], [db]), statique ou générée dynamiquement depuis un cloud provider.
Playbook
Un fichier YAML qui associe des hosts à une liste ordonnée de tâches et de rôles à exécuter.
Module
L'unité d'action réutilisable (apt, copy, service, template...). Chaque module encapsule sa propre logique d'idempotence.
Rôle
Un ensemble de tâches, variables, templates et handlers packagés de façon réutilisable, l'équivalent d'un module bien organisé pour un composant d'infrastructure (nginx, postgres...).
Idempotence
Le principe central : exécuter le même playbook deux fois de suite doit produire le même état final, sans effet de bord la seconde fois.
Handler
Une tâche déclenchée uniquement si une autre tâche a réellement changé quelque chose (ex : redémarrer nginx seulement si sa config a changé).

Templates Jinja2

Le module template génère un fichier de configuration à partir d'un gabarit Jinja2 et des variables de l'inventaire. C'est la façon dont un même rôle nginx produit une configuration différente par environnement sans dupliquer le fichier.

# templates/nginx.conf.j2
server {
  listen {{ nginx_port | default(80) }};
  server_name {{ inventory_hostname }};
{% for upstream in upstreams %}
  location /{{ upstream.path }} {
    proxy_pass http://{{ upstream.host }}:{{ upstream.port }};
  }
{% endfor %}
}

# task correspondante
- name: Déployer la config nginx
  template:
    src: nginx.conf.j2
    dest: /etc/nginx/sites-available/app.conf
  notify: restart nginx

Les filtres (| default(...)), les boucles ({% for %}) et les conditions ({% if %}) font de Jinja2 un vrai langage de templating, pas un simple remplacement de variables.

Inventaire dynamique

Un inventaire statique (inventory.ini) devient vite intenable dès que des machines sont créées/détruites dynamiquement dans le cloud. Un plugin d'inventaire dynamique interroge directement le provider pour construire la liste des hosts à chaque exécution.

# inventory/aws_ec2.yml
plugin: amazon.aws.aws_ec2
regions: [eu-west-3]
filters:
  tag:Environment: production
keyed_groups:
  - key: tags.Role
    prefix: role

Combiné à des groupes générés automatiquement (keyed_groups), un playbook peut cibler « tous les hosts taggés role_web en production » sans jamais maintenir de liste d'IP à la main.

Cheat sheet

# Exécution
ansible-playbook -i inventory.ini site.yml
ansible-playbook site.yml --check          # dry-run
ansible-playbook site.yml --limit web       # cibler un groupe
ansible-playbook site.yml --tags deploy     # exécuter un sous-ensemble

# Ad-hoc (une commande ponctuelle, sans playbook)
ansible web -m ping
ansible web -m shell -a "uptime"

# Exemple de tâche idempotente
- name: Installer nginx
  apt:
    name: nginx
    state: present
  notify: restart nginx

handlers:
  - name: restart nginx
    service:
      name: nginx
      state: restarted

# Boucle & condition
- name: Installer plusieurs paquets
  apt: { name: "{{ item }}", state: present }
  loop: [nginx, postgresql, redis-server]
  when: ansible_os_family == "Debian"

Bonnes pratiques

Ansible Vault

Chiffrer les secrets (mots de passe, clés API) directement dans le repo Git avec ansible-vault, plutôt que de les laisser en clair dans les variables.

Rôles plutôt que playbooks monolithiques

Un rôle par responsabilité (nginx, postgres, monitoring) : testable, réutilisable entre projets, partageable via Ansible Galaxy.

Toujours tester en --check

Le mode dry-run signale ce qui changerait sans l'appliquer, précieux avant de toucher une flotte de production.

Variables par environnement

Séparer group_vars/staging et group_vars/production plutôt que des conditions if dispersées dans les tâches.

Questions d'entretien fréquentes

Pourquoi Ansible plutôt que Puppet/Chef ?

Aucun agent à déployer et maintenir sur les cibles : la connexion SSH suffit. Le coût d'entrée est plus faible, au prix d'un modèle légèrement moins adapté à des synchronisations continues très fréquentes.

Qu'est-ce que l'idempotence et pourquoi est-ce essentiel ?

Rejouer la même tâche ne doit rien changer si l'état désiré est déjà atteint. Sans cette garantie, on ne peut pas rejouer un playbook en confiance après un échec partiel.

Rôle vs playbook ?

Le playbook orchestre ; le rôle encapsule une responsabilité réutilisable (variables, tâches, templates, handlers) qu'un ou plusieurs playbooks peuvent inclure.

Comment gérer un inventaire de machines qui changent en permanence (cloud) ?

Un plugin d'inventaire dynamique (aws_ec2, azure_rm...) interroge le provider à chaque run pour reconstruire la liste des hosts à partir de tags, plutôt que de maintenir un fichier statique voué à devenir obsolète.

Comment un même rôle produit-il une configuration différente par environnement ?

Via un template Jinja2 dont les valeurs proviennent des variables de group_vars/<environnement> : le gabarit reste unique, seules les variables changent d'un environnement à l'autre.
