System Design

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Les blocs de construction récurrents d'un système à grande échelle (DNS, CDN, load balancer, cache, base de données) et la logique de compromis qui guide le choix de chacun, plutôt qu'une réponse unique valable partout.

Vue d'ensemble

Le system design ne cherche pas la solution parfaite mais le compromis le plus adapté à des contraintes données : volume d'utilisateurs, cohérence exigée, budget, latence tolérée. Une bonne réponse d'entretien commence toujours par clarifier ces contraintes avant de dessiner quoi que ce soit.

Composants clés

Load balancer
Répartit le trafic entre plusieurs instances applicatives, avec un healthcheck qui retire automatiquement une instance défaillante de la rotation.
Cache
Réduit la charge sur la base de données pour les lectures fréquentes. Le vrai sujet n'est pas de le mettre en place mais de gérer son invalidation quand la donnée sous-jacente change : la source classique de bugs de cache.
Base de données SQL vs NoSQL
SQL pour des relations fortes et des transactions ACID ; NoSQL (clé-valeur, document) pour un scaling horizontal natif au prix d'une cohérence parfois éventuelle plutôt qu'immédiate.
Message queue
Découple un traitement long (envoi d'email, génération de rapport) du chemin critique de la requête utilisateur, en absorbant les pics de charge.
Réplication & sharding
La réplication duplique la même donnée sur plusieurs nœuds (lecture scalable, tolérance de panne). Le sharding répartit des sous-ensembles différents de données sur plusieurs nœuds (écriture scalable), au prix de requêtes cross-shard plus complexes.

Patterns de communication

REST synchrone

Le client attend la réponse avant de continuer. Simple à raisonner, mais un service lent ralentit directement tous ses appelants, faute de découplage temporel.

Messagerie asynchrone

Le producteur dépose un message et continue sans attendre ; le consommateur le traite à son rythme. Absorbe les pics de charge, au prix d'une cohérence différée plutôt qu'immédiate.

gRPC

RPC binaire (Protobuf) plus performant que du JSON/REST pour de la communication interne service-à-service à fort volume, avec un contrat fortement typé, moins adapté à une API publique consommée par des navigateurs.

Rate limiting

Protège un service d'un client (ou d'un pic) qui dépasserait sa capacité. Algorithmes courants : token bucket (autorise des rafales contrôlées) ou sliding window (compte précis sur une fenêtre glissante).

Scalabilité

Vertical vs horizontal

Scaler verticalement (machine plus grosse) est simple mais plafonne vite et introduit un point de panne unique. Scaler horizontalement (plus d'instances) demande des services sans état (stateless), mais tient dans la durée.

CAP theorem

En cas de partition réseau, un système distribué doit choisir entre cohérence (Consistency) et disponibilité (Availability), impossible de garantir les deux simultanément à ce moment-là.

Idempotence des API

Une requête rejouée (retry réseau) ne doit pas dupliquer l'effet, essentiel dès qu'un client peut retenter un appel après un timeout.

Consistent hashing

Répartit les clés sur les nœuds d'un cache ou d'une base shardée de façon à ce qu'ajouter/retirer un nœud ne redistribue qu'une petite fraction des clés. Sans ça, changer le nombre de nœuds invaliderait presque tout le cache d'un coup.

Étude de cas : concevoir un raccourcisseur d'URL

Un exercice classique d'entretien, qui illustre bien la méthode plutôt qu'une réponse à réciter par cœur.

01Contraintes : ratio lecture/écriture très déséquilibré (bien plus de redirections que de créations de lien), latence de redirection critique.
02Génération de la clé courte : encoder en base62 un compteur distribué (ou hasher l'URL et tronquer, avec gestion des collisions).
03Écriture : persister le mapping clé→URL en base, avec un cache en écriture pour les liens créés en masse.
04Lecture : un cache (Redis) devant la base absorbe l'essentiel du trafic de redirection, largement dominant sur ce cas d'usage.
05Scalabilité : sharder par clé courte si le volume dépasse une seule base, avec consistent hashing pour limiter la redistribution lors d'un ajout de nœud.

Méthode pour un entretien de system design

01Clarifier les exigences fonctionnelles et les contraintes chiffrées (utilisateurs actifs, volume de données, latence tolérée).
02Estimer les ordres de grandeur (requêtes/seconde, stockage) avant de dessiner quoi que ce soit.
03Proposer une architecture minimale qui répond au besoin, puis l'étoffer point par point (cache, réplication, CDN).
04Identifier explicitement les goulots d'étranglement et les compromis assumés : c'est souvent ce point qui distingue une bonne réponse d'une excellente.

Questions fréquentes

Comment gérer l'invalidation de cache ?

Selon le besoin : TTL court pour une fraîcheur acceptable, invalidation explicite à l'écriture pour une cohérence stricte, ou write-through pour garder cache et base synchronisés à chaque écriture.

Réplication vs sharding ?

La réplication copie les mêmes données partout (scale la lecture, tolère les pannes). Le sharding répartit des données différentes sur des nœuds différents (scale l'écriture), au prix de requêtes cross-shard plus coûteuses.

Comment rendre une API idempotente ?

Un identifiant unique de requête (idempotency key) côté client, vérifié côté serveur avant traitement : un retry avec la même clé renvoie le résultat déjà produit plutôt que de le rejouer.

Pourquoi le consistent hashing plutôt qu'un modulo simple pour répartir des clés ?

Avec un modulo (hash(clé) % N), changer N redistribue presque toutes les clés d'un coup. Le consistent hashing place nœuds et clés sur un même anneau : ajouter ou retirer un nœud ne redistribue que les clés voisines de ce nœud, pas l'ensemble.

Quand préférer une messagerie asynchrone à un appel REST synchrone ?

Dès que l'appelant n'a pas besoin du résultat immédiat pour continuer (envoi d'email, génération de rapport) ou que le service appelé doit rester protégé d'un pic de charge : le découplage absorbe la charge au prix d'une cohérence différée.
