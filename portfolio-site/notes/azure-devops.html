Azure DevOps

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

La suite d'outils Microsoft qui couvre tout le cycle de vie logiciel : planification (Boards), code (Repos), intégration et déploiement continus (Pipelines), gestion d'artefacts (Artifacts). C'est la même chaîne que j'utilise pour automatiser build et déploiement sur mes projets .NET.

Vue d'ensemble

Azure DevOps couvre le cycle Plan → Code → Build → Test → Release → Monitor sur une plateforme unique, intégrée nativement à l'écosystème .NET/Azure. La pièce la plus structurante au quotidien reste Pipelines : un pipeline YAML versionné avec le code, qui compile, teste et déploie automatiquement à chaque push.

Les 5 piliers

Boards

Gestion de backlog agile : work items, sprints, tableaux Kanban, liés directement aux commits et pull requests qui les résolvent.

Repos

Dépôts Git managés, avec des politiques de branche (revue obligatoire, build qui doit passer avant merge).

Pipelines

CI/CD as code en YAML : build, tests, packaging et déploiement multi-environnements (dev → staging → prod).

Artifacts

Registre de packages (NuGet, npm, Maven) internes à l'organisation, versionnés et partagés entre projets.

Test Plans

Gestion de campagnes de tests manuels et exploratoires, complémentaire aux tests automatisés du pipeline.

Anatomie d'un pipeline YAML

trigger:
  branches: { include: [main] }

pool:
  vmImage: ubuntu-latest

stages:
  - stage: Build
    jobs:
      - job: BuildAndTest
        steps:
          - task: UseDotNet@2
            inputs: { version: "9.x" }
          - script: dotnet restore
          - script: dotnet build --configuration Release
          - script: dotnet test --logger trx

  - stage: Deploy
    dependsOn: Build
    condition: succeeded()
    jobs:
      - deployment: ToStaging
        environment: staging
        strategy:
          runOnce:
            deploy:
              steps:
                - script: echo "Déploiement vers staging"

Chaque stage ne s'exécute que si la précédente réussit (dependsOn + condition) : impossible de déployer un build qui ne compile pas ou dont les tests échouent.

Templates réutilisables

Dès que plusieurs projets partagent la même logique de build (restore/build/test .NET, par exemple), un template extrait cette logique dans un fichier unique, inclus partout où c'est nécessaire, pour éviter que 5 pipelines dérivent chacun de leur côté au fil du temps.

# templates/dotnet-build.yml
parameters:
  - name: dotnetVersion
    default: "9.x"
steps:
  - task: UseDotNet@2
    inputs: { version: ${{ parameters.dotnetVersion }} }
  - script: dotnet restore
  - script: dotnet build --configuration Release

# azure-pipelines.yml
stages:
  - stage: Build
    jobs:
      - job: BuildAndTest
        steps:
          - template: templates/dotnet-build.yml
            parameters: { dotnetVersion: "9.x" }

Une évolution du process de build (ajout d'un scan de sécurité, par exemple) se fait alors à un seul endroit, et se propage à tous les pipelines qui référencent le template.

Agents & environnements

Agents hébergés par Microsoft
Machines éphémères fournies par Azure DevOps (vmImage: ubuntu-latest), sans maintenance, mais avec des minutes de build limitées selon le plan et sans accès à un réseau interne.
Agents self-hosted
Des machines qu'on enregistre soi-même dans un pool : nécessaires dès qu'un build a besoin d'un accès réseau interne (base de données on-premise) ou d'outils/licences spécifiques non disponibles sur les images Microsoft.
Environments & approbations
Un environment Azure DevOps (staging, production) peut exiger une approbation manuelle d'une personne ou d'un groupe désigné avant que le déploiement ne se poursuive : le point de contrôle humain avant la prod.
Service connections
La façon dont un pipeline s'authentifie auprès d'un service externe (Azure, Docker Hub, un cluster Kubernetes) sans exposer les identifiants dans le YAML.

Bonnes pratiques CI/CD

Pipeline as code

Le YAML vit dans le repo, versionné et revu en pull request comme n'importe quel autre changement.

Environnements avec approbation

Un déploiement en production peut exiger une approbation manuelle explicite, contrairement à staging qui se déploie automatiquement.

Variable groups & Key Vault

Secrets injectés depuis Azure Key Vault au moment du run, jamais en clair dans le YAML.

Politiques de branche

Build obligatoire au vert et revue de code requise avant de pouvoir merger sur main.

Questions d'entretien fréquentes

Différence entre intégration continue et déploiement continu ?

L'intégration continue compile et teste automatiquement chaque changement. Le déploiement continu va plus loin : livrer automatiquement ce build validé jusqu'en production, sans intervention manuelle (à distinguer de la « delivery » continue, qui s'arrête juste avant la mise en prod, en attente d'une validation).

Comment gérer des secrets dans un pipeline ?

Variable groups liés à Azure Key Vault, jamais en variable en clair dans le YAML ni committés dans le repo.

Comment empêcher un déploiement si les tests échouent ?

Le stage de déploiement déclare une dépendance (dependsOn) sur le stage de build/test avec la condition succeeded() : il ne se déclenche tout simplement pas sinon.

Quand utiliser un agent self-hosted plutôt qu'un agent Microsoft ?

Dès qu'un build a besoin d'un accès réseau interne (base de données on-premise, VPN d'entreprise) ou d'outils spécifiques non disponibles sur les images standard, au prix de la maintenance de cette machine.

Comment éviter que plusieurs pipelines divergent au fil du temps ?

Extraire la logique commune (restore/build/test) dans un template YAML partagé, référencé par chaque pipeline avec ses propres paramètres : un seul endroit à faire évoluer plutôt que N copies qui dérivent chacune de leur côté.
