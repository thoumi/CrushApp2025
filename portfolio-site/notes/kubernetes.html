Kubernetes

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Ce que Docker Compose ne fait plus à l'échelle d'un cluster : Kubernetes prend le relais pour planifier, redémarrer, scaler et exposer des conteneurs sur plusieurs nœuds, avec un état désiré déclaré plutôt qu'une suite de commandes impératives.

Vue d'ensemble

Kubernetes (K8s) est un orchestrateur : on lui décrit un état désiré (« 3 réplicas de cette image, exposés sur ce port »), et une boucle de contrôle permanente compare cet état à la réalité du cluster pour la corriger en continu : nœud qui tombe, pod qui crashe, montée en charge. C'est ce passage de l'impératif (« lance ce conteneur ») au déclaratif qui justifie sa complexité par rapport à Compose.

Architecture du cluster

Control PlaneAPI Server · etcd · Scheduler · Controller Manager
Node 1kubelet · kube-proxy · pods
Node 2kubelet · kube-proxy · pods
Node N…

Le control plane décide (où placer un pod, quoi corriger) ; chaque node exécute (kubelet démarre les conteneurs, kube-proxy gère le routage réseau local). etcd est la seule source de vérité de l'état du cluster, et sa sauvegarde est le premier réflexe avant toute opération risquée en production.

Objets clés

Pod
La plus petite unité déployable : un ou plusieurs conteneurs qui partagent réseau et stockage. On ne crée quasiment jamais un pod nu directement : il est géré par un contrôleur au-dessus.
Deployment
Gère un ensemble de pods identiques (ReplicaSet) et pilote les mises à jour progressives (rolling update) : de nouveaux pods démarrent avant que les anciens ne soient arrêtés, sans interruption de service.
Service
Adresse réseau stable devant un ensemble de pods éphémères. ClusterIP pour la communication interne, NodePort/LoadBalancer pour exposer vers l'extérieur.
Ingress
Couche de routage HTTP(S) au-dessus des Services : un seul point d'entrée qui route par host/path vers plusieurs services, avec TLS termination.
ConfigMap & Secret
Séparent la configuration et les données sensibles de l'image : même image, comportement différent selon l'environnement dans lequel elle est déployée.
StatefulSet
Comme un Deployment, mais pour les workloads avec état (bases de données) : identité réseau stable et volume dédié par réplica, dans un ordre de démarrage garanti.
Namespace
Cloisonnement logique (équipes, environnements) à l'intérieur d'un même cluster physique.

RBAC & sécurité d'accès

Le contrôle d'accès basé sur les rôles décide qui peut faire quoi sur quelles ressources, indispensable dès que plusieurs équipes partagent un même cluster.

Role & ClusterRole
Un Role définit des permissions dans un namespace donné ; un ClusterRole les définit à l'échelle du cluster entier (utile pour des ressources non-namespacées comme les nodes).
RoleBinding & ClusterRoleBinding
Associent un Role/ClusterRole à un utilisateur, groupe ou ServiceAccount. Sans binding, un rôle défini n'a strictement aucun effet.
ServiceAccount
L'identité qu'utilise un pod pour s'authentifier auprès de l'API Server. Par défaut c'est le default ServiceAccount du namespace, à restreindre explicitement plutôt qu'à laisser en accès large par défaut.
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: staging, name: pod-reader }
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]

Helm

Le gestionnaire de paquets de Kubernetes : un chart Helm packages un ensemble de manifestes YAML paramétrables, pour éviter de dupliquer 10 fichiers presque identiques entre dev, staging et prod.

helm install mon-app ./chart -f values-staging.yaml
helm upgrade mon-app ./chart --set image.tag=1.4.0
helm rollback mon-app 2          # revenir à la révision 2
helm list -n staging

Chaque values.yaml paramètre le même chart pour un environnement différent (réplicas, tag d'image, ressources) : la logique de templating reste unique, seules les valeurs changent.

Cheat sheet kubectl

# État du cluster
kubectl get nodes
kubectl get pods -n mon-namespace
kubectl get all -A
kubectl top pods -n mon-namespace           # conso CPU/mémoire en direct

# Déploiement
kubectl apply -f deployment.yaml
kubectl rollout status deployment/api
kubectl rollout undo deployment/api        # revenir en arrière
kubectl rollout history deployment/api     # historique des révisions

# Debug
kubectl describe pod api-7d4f9-x2z8k       # events, dernières erreurs
kubectl logs -f api-7d4f9-x2z8k
kubectl logs --previous api-7d4f9-x2z8k    # logs du conteneur précédent (avant crash)
kubectl exec -it api-7d4f9-x2z8k -- sh
kubectl get events --sort-by=.lastTimestamp -n mon-namespace

# Scaling
kubectl scale deployment/api --replicas=5
kubectl autoscale deployment/api --min=2 --max=10 --cpu-percent=70

# RBAC & contexte
kubectl auth can-i delete pods --as=system:serviceaccount:staging:ci-bot
kubectl config use-context production

Bonnes pratiques

Requests & limits

Sans resources.requests/limits, un pod peut affamer tout le node ou être expulsé arbitrairement sous pression mémoire.

Liveness vs readiness

La liveness probe redémarre un pod bloqué ; la readiness probe le retire du Service tant qu'il n'est pas prêt à recevoir du trafic. Confondre les deux provoque des redémarrages en boucle inutiles.

Jamais de :latest

Un tag immuable (version ou SHA) rend un rollback réellement possible.

PodDisruptionBudget

Garantit un nombre minimum de réplicas disponibles pendant une maintenance de nœud planifiée.

Secrets via un vault externe

Les Secrets Kubernetes ne sont encodés qu'en base64 par défaut, pas chiffrés au repos sans configuration supplémentaire (encryption at rest, ou Vault/External Secrets).

GitOps

L'état désiré du cluster versionné dans Git (Argo CD, Flux) plutôt que des kubectl apply manuels non traçables.

Questions d'entretien fréquentes

Pod vs Deployment vs ReplicaSet ?

Le Pod exécute les conteneurs. Le ReplicaSet garantit qu'un nombre donné de pods identiques tourne en permanence. Le Deployment pilote le ReplicaSet et gère les mises à jour progressives et les rollbacks.

Comment un Service trouve-t-il ses pods ?

Par correspondance de labels (selector), pas par nom ou par IP, qui sont éphémères pour un pod.

Liveness vs readiness probe ?

Liveness : « ce pod est-il bloqué, faut-il le redémarrer ? ». Readiness : « ce pod peut-il recevoir du trafic maintenant ? ». Un pod peut être vivant mais pas prêt (démarrage en cours).

Comment gérer une base de données sur K8s ?

Via un StatefulSet avec un volume persistant par réplica, ou plus souvent en la laissant en dehors du cluster (managed database) tant que le gain d'opérer un état stateful in-cluster ne dépasse pas le risque.

À quoi sert un ServiceAccount, et pourquoi ne pas laisser le default ?

C'est l'identité qu'un pod présente à l'API Server. Le ServiceAccount default a souvent plus de droits que nécessaire pour un workload donné ; en créer un dédié par application avec un RoleBinding minimal applique le principe du moindre privilège.

Pourquoi utiliser Helm plutôt que des manifestes YAML bruts ?

Dès que la même stack doit être déployée sur plusieurs environnements, dupliquer des YAML presque identiques devient une source d'erreurs. Un chart Helm centralise le templating et ne fait varier que les valeurs par environnement.
