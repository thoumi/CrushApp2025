AWS

Fiche de synthèse par Lhoussaine Thoumi · Mise à jour le 3 août 2026

Une carte mentale des services AWS que je recroise le plus souvent, organisée par le problème qu'ils résolvent (calcul, stockage, données, réseau, sécurité) plutôt que par ordre alphabétique.

Vue d'ensemble

AWS loue à la demande ce qu'une infrastructure on-premise possède en dur : capacité de calcul, stockage, réseau. L'intérêt n'est pas seulement économique (pay-as-you-go) mais opérationnel : scaler horizontalement, changer de région, ou remplacer une brique managée sans racheter de matériel.

Services par domaine

Compute

EC2 : VM à la demande, contrôle total de l'OS. Lambda : fonctions serverless facturées à l'exécution, sans serveur à gérer. ECS/EKS : orchestration de conteneurs (Docker/Kubernetes managés).

Stockage

S3 : stockage objet durable (11 neufs), pour fichiers, backups, contenu statique. EBS : disque bloc attaché à une instance EC2, comme un disque dur virtuel.

Base de données

RDS : PostgreSQL/MySQL/SQL Server managés (backups, patching automatiques). DynamoDB : NoSQL clé-valeur, latence à un chiffre de milliseconde, scaling horizontal natif.

Sécurité

IAM : qui (utilisateur, rôle, service) peut faire quoi sur quelle ressource. VPC : réseau privé isolé où vivent les ressources.

Monitoring

CloudWatch : métriques, logs, alarmes, le premier réflexe pour diagnostiquer un incident en production.

Réseau

Route 53 : DNS managé. CloudFront : CDN pour rapprocher le contenu des utilisateurs. ALB/NLB : répartition de charge.

Réseau & sécurité : les bases IAM/VPC

IAM : utilisateur, groupe, rôle, policy
Une policy JSON décrit des permissions (actions autorisées sur des ressources). Un rôle est assumé temporairement par un service ou un utilisateur fédéré, et c'est la méthode recommandée plutôt que des clés d'accès statiques.
Principe du moindre privilège
Chaque rôle ne reçoit que les permissions strictement nécessaires à sa tâche, jamais *:* par confort.
VPC, subnets publics/privés
Un VPC isole un réseau virtuel ; les subnets publics ont une route vers un Internet Gateway, les subnets privés en sont dépourvus et sortent via un NAT Gateway si besoin.
Security Groups
Pare-feu stateful au niveau de l'instance : seul le trafic explicitement autorisé en entrée passe, la réponse est automatiquement permise.

Well-Architected Framework

Le référentiel qu'AWS utilise lui-même en revue d'architecture : cinq (à l'origine six) piliers pour évaluer une architecture cloud au-delà du simple « est-ce que ça marche ? ».

Excellence opérationnelle

Automatiser les changements, anticiper les échecs, apprendre de chaque incident plutôt que de le refermer sans analyse.

Sécurité

Moindre privilège, chiffrement au repos/en transit par défaut, traçabilité complète des accès via CloudTrail.

Fiabilité

Se remettre automatiquement d'une panne (auto-healing, multi-AZ) plutôt que de dépendre d'une intervention manuelle.

Performance

Choisir le bon type de ressource pour la charge réelle, et revoir ce choix quand la charge change plutôt que de sur-dimensionner par précaution.

Optimisation des coûts

Ne payer que pour ce qui est réellement utilisé (instances réservées, auto-scaling, suppression des ressources orphelines).

Durabilité

Le pilier le plus récent : mesurer et réduire l'empreinte carbone d'une charge de travail, par exemple en choisissant une région à mix électrique plus favorable.

Lambda en détail

Le service le plus représentatif du serverless : on déploie une fonction, AWS gère entièrement le provisionnement, le scaling et la facturation à la milliseconde d'exécution.

Triggers
Une Lambda ne s'exécute jamais toute seule : elle est déclenchée par un événement (requête API Gateway, fichier déposé sur S3, message SQS, planification EventBridge...).
Cold start
Le délai d'initialisation d'un nouvel environnement d'exécution avant le premier appel. Les runtimes interprétés (Node, Python) démarrent plus vite que la JVM ; le provisioned concurrency élimine ce délai au prix d'une capacité pré-chauffée en permanence, donc payée en continu.
Layers
Du code ou des dépendances partagés entre plusieurs fonctions (un SDK interne, par exemple), packagés une fois et référencés par chaque Lambda plutôt que dupliqués dans chaque déploiement.
Limites
15 minutes d'exécution maximum et une mémoire plafonnée : au-delà, ECS/Fargate ou EC2 deviennent le bon choix, Lambda n'est pas fait pour du traitement longue durée.

Cheat sheet CLI

# Identité & configuration
aws sts get-caller-identity
aws configure

# S3
aws s3 cp fichier.txt s3://mon-bucket/
aws s3 sync ./dist s3://mon-bucket/ --delete

# EC2
aws ec2 describe-instances --query "Reservations[].Instances[].[InstanceId,State.Name]"

# Logs
aws logs tail /aws/lambda/ma-fonction --follow

# Lambda
aws lambda invoke --function-name ma-fonction --payload '{}' out.json
aws lambda update-function-code --function-name ma-fonction --zip-file fileb://build.zip

# IAM
aws iam list-attached-role-policies --role-name ma-fonction-role
aws sts assume-role --role-arn arn:aws:iam::123456789012:role/deploy --role-session-name ci

Bonnes pratiques

Infrastructure as Code

Terraform ou CloudFormation plutôt que des clics dans la console : reproductible, versionné, revu en pull request.

Pas de clés d'accès en dur

Rôles IAM assumés par les services (EC2, Lambda) plutôt que des AWS_ACCESS_KEY_ID committés ou en variable d'environnement statique.

Multi-AZ pour la haute disponibilité

Répartir les ressources critiques sur plusieurs zones de disponibilité pour survivre à la perte d'un datacenter.

Budgets & alarmes de coût

AWS Budgets pour être alerté avant qu'une ressource oubliée (instance, snapshot) ne fasse dériver la facture.

Questions d'entretien fréquentes

EC2 vs Lambda, quand choisir quoi ?

Lambda pour du traitement court et événementiel sans gestion de serveur ; EC2 quand on a besoin de contrôle total sur l'OS, de process longue durée, ou de charges qui dépassent les limites d'exécution serverless.

Comment sécuriser l'accès entre deux services AWS ?

Un rôle IAM assumé par le service appelant, avec une policy limitée aux actions nécessaires. Jamais de clé d'accès statique partagée entre services.

RDS vs DynamoDB ?

RDS pour des données relationnelles avec transactions ACID et requêtes complexes ; DynamoDB pour un accès clé-valeur à très faible latence et un scaling horizontal natif, au prix d'un modèle de requêtage plus contraint.

Qu'est-ce qu'un cold start Lambda, et comment le limiter ?

Le délai d'initialisation d'un nouvel environnement d'exécution avant le premier appel. On le limite en choisissant un runtime léger, en réduisant la taille du package déployé, ou avec du provisioned concurrency si la latence est critique.

Comment appliquer le principe du moindre privilège sur AWS ?

Une policy IAM dédiée par rôle, qui ne liste que les actions et ressources réellement nécessaires. Jamais une policy générique *:* par confort, même en environnement de test.
